# Working synthetic doctor demo

Local URL: `http://localhost:3001/doctor.html`. Launch from the repository with `npm start`.
Doctor account: `doctor@dai-synthetic.invalid`; patient account: `mother@dai-synthetic.invalid`. The launcher prints the configured synthetic password. Its default remains `Dai-Synthetic-2026!`.

## What startup now connects

The local cohort importer previously never invoked `seed-doctor-activity.cjs`. Startup now calls it both after a first import and when the cohort is already imported. That additive, one-time fixture creates linked clinic appointments, synthetic measurement records, real generated report files, report shares and completed historical clinic events. It does not restore revoked summary shares. Active relationship checks exclude revoked patients. New fixture appointments include their source facility UUID.

`seed-doctor-demo-day.cjs` adds a bounded set of today's synthetic bookings for already assigned patients: up to two child appointments, one postpartum appointment and two ANC appointments per verified, linked fictional doctor. Children must already belong to that mother. No new patients, assignments, diagnoses, risk flags or clinical completions are generated by this daily schedule. The local-only seed is marked by calendar date. Starting again on the same day preserves appointment edits, cancellations and queue actions; starting on another day can add a new day's demonstration bookings. Existing bookings are respected. A doctor without assigned children does not receive invented child ownership.

The doctor workspace now reads the hospital's `roster_entry` data as well as explicit on-call entries. A scheduled shift is displayed as a recorded roster, with its date, and is not represented as confirmed presence. Hospital capacity and stock remain sourced snapshots; they are not reservations or live readiness guarantees.

## Local messages

The new API is restricted to `DAI_LOCAL=true` and `DAI_DEMO=true`, synthetic email accounts, verified clinicians, existing unrevoked care connections and allowed doctor sharing. It does not broaden production access.

- `GET /api/demo/care-messages/contacts`
- `GET /api/demo/care-messages/thread?peer_id=…`
- `POST /api/demo/care-messages/thread` with `peer_id`, `text` and a v4 UUID `client_id`.

Read/send operations recheck access in a transaction and audit metadata without copying message text into the audit trail. Messages stay in `demo_care_messages` in the local database. No AI processing, SMS, email, external delivery or emergency monitoring is provided. Reads return at most the latest 100 messages; refresh is explicit. A retry with the same client ID/content does not duplicate a saved message. The frontend escapes message text, preserves drafts on failure and uses a bounded request timeout.

## Validation and limits

Sixteen Node tests passed: privacy/CSV, real SQL/HTTP reporting and export isolation, doctor workspace access/revocation and versioned operations, clinic and daily seeding/idempotence, local messages and complete backend startup/patient timeline integration.

A real-browser check used the full generated cohort (2,000 mothers, 1,078 children, 144 doctors), actual login cookies and the Node backend. It visited 15 doctor panels; verified child filtering/search/reset, report/roster data, queue completion/reload, mobile layout and a two-session doctor/patient message/reply/reload exchange. No JavaScript errors or server-side API failures occurred in those checked paths. The dedicated population UI check also exercised empty/error states and CSV downloads.

The demo does not claim live ambulance GPS, real-world appointment booking, external message delivery, model-based medical predictions or automatically confirmed clinical/resource readiness. Such missing information stays explicitly unknown. No real patient records or paid model calls were used.

## Installation

The separate functionality installer targets your pushed `main` commit `26f61cd`, which already contains the population analytics update. It validates every supported file before writing, backs up replaced files under Git metadata and never bundles `.env`, databases, report uploads or installed dependencies.

The population report migration is already part of the preceding update. `npm start` applies the new additive `demo_care_messages.sql` migration. Separately managed PostgreSQL deployments must apply it before deploying the messages module; the messages API remains disabled outside local demo mode.
